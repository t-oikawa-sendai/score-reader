## 1. Purpose（目的）

本設計書群は、完成版 MusicXML 作成支援システムへ到達するための検証結果・設計判断・未確定事項を整理したプロトタイプ段階の設計ガイドラインである。本文書はそのうち背景・課題・要求・成功基準を定義し、要件定義・設計フェーズの前提とすることを目的とする。

開発段階の分類（プロトタイプ検証段階 / 完成版MusicXML作成支援システムの本実装段階）は `README.md` §1 Development Stage Classification を参照する。現行プロトタイプ `verify_score.py` はプロトタイプ検証段階における単一 MusicXML 構造検査の検証実装である。

本文書の対象読者は、設計者・開発者・プロジェクトオーナーである。

## 3. Out of Scope（対象外範囲）

以下は本プロジェクトのスコープ外とする。自動修正、自動統合、Web UI、原本 PDF 横並び画面は、現時点で定義する本実装段階には含めず、将来検討事項として扱う（`README.md` §1 Development Stage Classification 参照）。

| 対象外項目 | 理由 |
|---|---|
| MusicXML の完全自動正誤判定 | 現技術では音高・音価・声部の正誤を機械的に確定できない |
| 原本 PDF との内容一致確認 | MusicXML だけでは原本 PDF の内容を復元・比較できない |
| 完成版アプリケーションの実装 | 本プロジェクトはプロトタイプ・検証フェーズを目的とする |
| 楽譜編集・修正機能 | MuseScore 等の既存ツールが担当する領域である |
| 音声再生・楽譜表示機能 | 本ツールの目的は検査結果の出力であり、再生・表示は対象外 |
| 複数 MusicXML の自動マージ・統合 | 複数 OMR 結果の比較は人間の判断を要するため自動化対象外 |
| solacom-main 等、他システムとの連携 | score-reader は独立したシステムであり、他システムと無関係 |

## 4. Assumptions（前提条件）

本文書の内容が成立するために必要な前提を以下に示す。

**OMR・入力に関する前提**

- ユーザーは外部 OMR サービス（Newzik 等）により原本 PDF から MusicXML を取得済みであること
- 入力 MusicXML は `music21.converter.parse` が読み込める形式であること
- 1 回の検査対象は単一 MusicXML ファイルであること

**技術的前提**

- 現技術では、楽譜 PDF から MusicXML への**完全自動化は困難**であること
- OMR が生成した MusicXML には、音高・音価・声部・記号に誤認識・欠落が混入しうること
- 複数 OMR の結果が一致していても、同じ誤認識を出している可能性があること
- MusicXML の内部整合性が正常でも、原本 PDF と内容が異なる可能性があること

**Prototype の位置づけ**

- `verify_score.py`（`prototype/src/`）は技術検証用プロトタイプであり、**正式完成版ではない**
- 現段階のプロトタイプは単一 MusicXML の内部整合性検査に限定する
- プロトタイプの検証結果が、本設計の要求・要件定義に反映される

**人間確認に関する前提**

- score-reader の目的は**人間確認をゼロにすることではなく、確認対象を絞り込み確認作業を省力化すること**である
- 最終的な正確性の担保は原本 PDF との人間による目視照合が必要であること
- score-reader が警告・異常を検出しない場合でも、完全無欠を保証しないこと

**著作権・情報セキュリティに関する前提**

- テスト素材はパブリックドメイン楽譜に限定すること
- 著作権保護された譜面を公開リポジトリへ登録しないこと
- 外部 OMR サービスへ譜面を送信する際は、利用規約と著作権条件を事前確認すること

**文書管理に関する前提**

- 本文書の Created Date は Document Info（2026-06-09）を参照する

## 5. Definition Details（定義内容）

### 5.1 Background and Purpose（背景・課題・目的）

#### 背景

楽譜 PDF のデータ化（MusicXML 化）作業では、OMR（Optical Music Recognition）サービスを利用して楽譜 PDF を MusicXML に変換し、MuseScore 等で開いて人間が確認・修正する運用が行われている。

現行運用フロー:

```
原本 PDF → OMR サービス（例: Newzik） → MusicXML → MuseScore → 人手で確認・修正
```

#### 課題

現時点の OMR サービスは精度に大きな課題が残っており、OMR 出力 MusicXML をそのまま完成版として扱えない。

**OMR 精度の参考値（Newzik、利用者ヒアリングによる体感値）**

| 対象 | 精度参考値 |
|---|---:|
| 簡単な楽譜 | 約 95% |
| 難しい楽譜の音符の高さ・長さ | 約 70% |
| テキスト指示・臨時記号・多声部など | 30% 未満の場合あり |

上記は公式保証値ではなく、利用者ヒアリングによる参考値である。

**誤認識・欠落が発生し得る主な要素**

音符（音高・音価）、臨時記号、休符、複数小節休符、小節番号、拍子・調号、テンポ、強弱記号、リハーサルマーク、タイ・スラー、連符・装飾音符、多声部記譜、打楽器譜 など。

**完全自動化が困難な技術要因**

| 要因 | 内容 |
|---|---|
| 音高判定の不確実性 | 加線・符頭位置・調号・臨時記号・オクターブ違いにより確定できない |
| 音価・リズム判定の不確実性 | 符尾・連桁・付点・連符・休符の誤認識により小節内拍数が崩れうる |
| 声部分離の不安定性 | 同一譜表内複数声部の上声・下声・休符補完がツール間で異なる |
| 和音構成音の欠落・過検出 | 重なった符頭・内声部の解釈により欠落や余分な音が発生しうる |
| タイ・スラー・記号類の解釈差 | 見た目が近く、開始・終了位置・小節またぎの扱いが不安定 |
| 小節対応ずれの連鎖 | 1箇所の小節ずれが以降の比較全体に影響する可能性がある |
| MusicXML 表現差 | 同じ楽譜内容でも OMR ツールごとに XML 表現が異なる |
| 複数 OMR 間の同一誤認識 | 複数結果が一致しても同じ誤認識を出している可能性がある |

**作業負荷の現状**

難しい楽譜では、OMR 出力の部分修正では済まず、MuseScore 上で音符を一つずつ手入力し直す場合があり、1 楽譜のデータ化に約 50 時間を要するケースがある（利用者ヒアリング）。

#### 人間確認が必要な理由

MusicXML 単体では確定できない問題が多数存在するため、人間による原本 PDF との照合は不可欠である。

| 問題 | 理由 |
|---|---|
| どの OMR 結果が正しいか | 原本 PDF を見ないと確定できない |
| 欠落した音符の正解 | MusicXML だけでは復元不能 |
| タイ・スラーの正しい接続 | 表現意図を含むため人間による原本照合が必要 |
| 連符・装飾音符の正解 | 原本照合が必要 |
| 複数 OMR 一致時の正しさ | 同じ誤認識が起きる可能性がある |

#### 目的

score-reader は、以下を目的とする。

1. **機械的に検出できる構造的異常・要確認箇所を自動で抽出する**（拍子不一致、移調情報欠落、パート間小節数不一致 など）
2. **人間が確認すべき範囲を絞り込み、確認作業を省力化する**
3. **自動化できること・人間確認が必要なこと・現技術では困難なことを明確に分離する**

**score-reader は人間確認をゼロにするシステムではない。** 確認対象を絞り込み、作業効率を最大化することが目的である。

### 5.3 User Stories and Use Cases（ユーザーストーリー・ユースケース概要）

詳細な機能要件は `02_REQUIREMENTS_DEFINITION.md` に記載する。

| ID | User Story / Use Case（ユーザーストーリー / ユースケース） |
|---|---|
| US-001 | 作業者として、OMR が生成した MusicXML を score-reader に渡すことで、拍子不一致・移調情報欠落・パート間小節数不一致などの構造的異常を自動で一覧取得したい。確認箇所を絞り込んで人手作業を効率化するため。 |
| US-002 | 作業者として、検査結果を人間可読テキスト形式または JSON 形式で出力したい。MuseScore での修正作業中に参照したり、後工程ツールに渡したりするため。 |
| US-003 | 作業者として、score-reader が「警告なし」を出した場合でも、それが完全無欠を保証するものではないことを明示的に知りたい。誤った安心感を持たずに原本照合を行うため。 |
| US-004 | 設計者として、複数の OMR サービスで同一 PDF を変換し、各出力の構造的特徴を比較した上で、人間が重点確認すべき箇所を絞り込みたい。複数 OMR が一致する箇所を暫定的に低優先度として扱うことで確認作業を効率化するため。 |
| US-005 | 設計者として、「自動化できること」「人間確認が必要なこと」「現技術では困難なこと」を明確に定義した設計書を残したい。将来の保守者・利用者が設計意図を誤解なく引き継ぐため。 |

### 5.5 Success Criteria and Acceptance Conditions（成功基準・受け入れ条件）

テスト工程での検証基準は `06_OPERATION_AND_HANDOFF.md` に記載する。以下はビジネス観点・利用者観点での成功基準である。

**自動化できること（score-reader が機械的に検出できること）**

| ID | Success Criteria / Acceptance Condition（成功基準・受け入れ条件） |
|---|---|
| SC-001 | MusicXML のパース可否を判定し、パース失敗時は `[FATAL]` を出力して終了コード 1 で終了できる |
| SC-002 | 各パートの移調楽器情報の有無と記音→実音の半音差を報告できる |
| SC-003 | 拍子記号に対する小節内音価合計の不一致（`[ANOMALY]`）および拍子未確定小節（`[WARN]`）を検出できる |
| SC-004 | 調号・拍子・テンポ変化イベントを小節番号付きで列挙できる |
| SC-005 | リハーサルマークの小節対応・空内容・重複を検出できる |
| SC-006 | 和音構成音数の分布とパート内主流音数からの相違（`[WARN]`）を報告できる |
| SC-007 | 複数パート間の小節数不一致（`[WARN]`）を検出できる |
| SC-008 | 検査結果を人間可読テキスト形式および JSON 形式で出力できる |

**人間確認が必要なこと（score-reader が判定しないこと）**

| ID | 人間確認が必要な理由 |
|---|---|
| HC-001 | 音高の正誤（符頭位置・加線・臨時記号・オクターブ違い）は MusicXML のみでは確定できない |
| HC-002 | 和音構成音数が原本譜と一致するかは人間が原本 PDF と照合して判断する |
| HC-003 | パート間小節数不一致時に、どのパートが正しいかは人間が判断する |
| HC-004 | 複数 OMR の結果が一致していても、原本 PDF との照合なしに正解と断定してはならない |
| HC-005 | `[WARN]` / `[ANOMALY]` が 0 件でも、score-reader は完全無欠を保証しない |

**現技術では困難なこと（現フェーズのスコープ外）**

| ID | 現技術では困難な理由 |
|---|---|
| ND-001 | タイ・スラー・連符・装飾音の正誤判定は構造解釈に人間の音楽的判断が必要 |
| ND-002 | 多声部・打楽器特殊記譜の完全な構造比較は現時点の OMR 精度では不安定 |
| ND-003 | 複数 OMR 出力の自動マージ・統合による正解 MusicXML の自動生成 |

**削減効果について**

削減効果は未実測であり、現時点では定量的な成功基準としない。実測設計・測定方法は将来検討事項の検討課題とする（TBD-003）。

## 7. Handoff to Detail Design（詳細設計への引き継ぎ）

要件定義・アーキテクチャ設計フェーズへ引き継ぐ、本要求定義での主要な設計意図を示す。

1. **「推測しない」設計原則の継承**: 検査結果は断定せず、読めない・確定できない箇所を `[WARN]` / `[ANOMALY]` として列挙する原則を、正式版設計でも継続すること（`02_REQUIREMENTS_DEFINITION.md`・`05_ARCHITECTURE_DESIGN.md` の制約参照）。

2. **「自動化できること」と「人間確認が必要なこと」の境界を保持**: §5.5 の SC / HC / ND 分類を要件定義（`02_REQUIREMENTS_DEFINITION.md`）の機能要件・非機能要件に反映すること。この境界を曖昧にしないこと。

3. **Prototype の記録を参照源とすること**: `prototype/src/verify_score.py` の検査項目 [1]〜[8] および出力仕様は、要件定義・アーキテクチャ設計の出発点として参照すること。ただし、正式版では仕様変更・拡張が生じうるため、プロトタイプ実装との差分を明示的に管理すること。

4. **完全自動化を約束しないこと**: 成功基準（§5.5）の「現技術では困難なこと」は、要件定義・UI 設計・運用設計においても利用者への誤解防止として一貫して扱うこと。
