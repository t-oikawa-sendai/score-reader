## 1. Purpose（目的）

**初回実装の承認（2026-11-01、ユーザー）**: 2入力、02 §5.8.3〜5.8.5の初回判定表に基づく対応・部分比較、P1/P2/P3/U、個別根拠を保持した集約、共通テストデータ保存、および15ケースの期待報告を初回範囲として承認した。3入力以上・一般の多声部対応・実 OMR 効果検証は未承認/未実施のまま維持する。本書の初回範囲はこの承認で確定し、範囲外の提案・ASKMEへ拡張しない。


本文書は**プロトタイプ検証段階**における `verify_score.py` が扱うデータの種別・取り扱い方針、および著作権・外部サービス利用・秘密情報に関するセキュリティ設計仕様を定義し、実装・運用フェーズの基準とすることを目的とする。

開発段階の境界は `01_REQUEST_DEFINITION.md` §2 Development Stage Classification を参照する。本実装確定スコープ（`02_REQUIREMENTS_DEFINITION.md` §5.8）における比較データ・レポート出力の取り扱い詳細は、本文書の Open Issues（TBD-002）で管理する。比較機能の実装可否は確定済みである。セキュリティ要求レベルは `02_REQUIREMENTS_DEFINITION.md` §5.2 に記載する。本文書の対象読者は、設計者・実装者・プロジェクトオーナーである。

## 2. Scope（対象範囲）

本書の初回承認範囲を本実装として扱い、その他の提案は未承認のまま区別する。§5.1以降の既存プロトタイプの記録は凍結時点の仕様・制約である。

| 対象 | 内容 |
|---|---|
| 入力データ | score-reader が読み込む MusicXML ファイル |
| 出力データ | 標準出力に出力するテキスト形式・JSON 形式の検査結果 |
| テスト素材 | `prototype/tests/` 配下に配置する検証用 MusicXML |
| 外部 OMR サービス連携データ | 外部 OMR サービスへ送信する楽譜 PDF・画像（score-reader の入力生成過程で発生する） |
| 秘密情報・認証情報 | API キー・トークン・秘密鍵・個人情報の取り扱い方針 |

| 対象外項目 | 理由 |

## 4. Assumptions（前提条件）

本文書の内容が成立するために必要な前提は `01_REQUEST_DEFINITION.md` §4 を継承する。以下はデータ・セキュリティ設計フェーズで追加する前提を示す。

- score-reader はデータベースを持たない。データは「入力 MusicXML（読み取り専用）」と「標準出力（テキスト/JSON）」のみで完結する
- OMR 出力 MusicXML は「正解データ」ではなく「確認対象データ」として扱う。score-reader の検査結果も同様に確認対象であり、正確性の保証とは区別する
- 外部 OMR サービスへの楽譜送信は、score-reader の処理スコープ外（利用者が事前に行う操作）であるが、著作権・利用規約の観点から本文書で方針を定める
- ライセンス分離の決定記録は本書 TBD-004 を参照する

## 5. Definition Details（定義内容）

### 5.1 Entity Definition and ER Diagram（エンティティ定義・ER図）

本文書では ER 図・エンティティ定義は対象外。理由: score-reader はデータベースを持たないローカル実行 CLI ツールであり、データは実行ごとにオンメモリで処理される。

代わりに、score-reader が扱うデータ種別を以下に整理する。

#### Entity List（データ種別一覧）

| Entity Name（データ種別） | Description（説明） |
|---|---|
| 入力 MusicXML | 利用者が指定する検査対象ファイル。読み取り専用・非破壊 |
| 出力テキスト / JSON | 検査結果。標準出力のみ。score-reader はファイルを生成しない |
| テスト素材 MusicXML | `prototype/tests/` 配下。楽曲の権利、エンコーディングの権利、加工・再配布条件を分けて確認する |
| 楽譜 PDF・画像（外部 OMR 入力） | score-reader の処理スコープ外。著作権・利用規約の確認が必要 |

**OMR 出力 MusicXML の位置づけ**

OMR が出力した MusicXML は「正解データ」ではなく「確認対象データ」である。`[WARN]` / `[ANOMALY]` が 0 件であっても、MusicXML の完全無欠を保証しない。

### 5.3 Data Access and Role Design（データアクセス権限・ロール設計）

score-reader はシングルユーザーのローカル実行 CLI ツールであり、認証・認可機能を持たない。データアクセス権限はローカルファイルシステムの OS 権限に委ねる。

| Role Name（ロール名） | Accessible Data / Permitted Operations（アクセス可能なデータ / 操作範囲） |
|---|---|
| 利用者（CLI 実行者） | 入力 MusicXML の読み取り（Read only）。標準出力の参照 |
| score-reader プロセス | 入力 MusicXML の読み取りのみ。ファイルの書き込み・削除・派生ファイル生成は禁止 |
| 開発者 | `prototype/tests/` 配下のテスト素材の追加・更新（§5.4 の権利確認を経ること） |

### 5.4 Personal and Confidential Data Policy（個人情報・機密データの取り扱い方針）

#### 個人情報

score-reader は利用者の個人情報を収集・保存・送信しない。出力（テキスト/JSON）に個人情報を含めない設計とする。

#### 著作権保護データ（Copyright Policy）

| 方針 | 内容 |
|---|---|
| リポジトリへの登録禁止 | 著作権保護された楽譜 PDF・MusicXML・画像・その他楽譜素材を公開リポジトリ（GitHub 等）へ登録しない |
| 権利の分離確認 | テスト素材は次を分けて確認する。楽曲・作曲物の権利状態 / MusicXML エンコーディングの権利・利用条件 / OMR・変換・編集による派生成果物の扱い / 公開 GitHub からの再配布が許可される範囲 |
| パブリックドメイン楽譜との混同禁止 | 楽曲がパブリックドメインでも、MusicXML エンコーディングが公開可能とは限らない |
| 法域の断定禁止 | 世界向け公開を前提とするため、米国で自由とされることだけで再配布可能と断定しない |
| MusicXML メタデータ | `<creator>` 等の値だけで作曲者や権利者を確定しない。公開前に除去または公開可否を確認する |
| 利用者の責任 | 入力 MusicXML の著作権状況は、利用者が事前に確認する責任を負う |
| 外部 OMR サービス利用時 | 外部 OMR サービスへ楽譜 PDF・画像を送信する場合は、利用規約・著作権条件を事前に確認する |
| 現行テスト素材の公開 | 現在公開中のテスト素材は権利確認中であり、公開可否は法的に未確定である。最終判断責任者は Takashi Oikawa である。公開判断の固定期限は設けない。権利判断が完了するまでの暫定措置は、その旨を明示した上での公開継続である |

未解決事項は TBD-005 に限定する。最終判断責任者、暫定措置、現時点の公開継続方針は確定済みである（本節）。

本節の記載は法律上の助言ではない。公開可否の最終判断責任者は Takashi Oikawa である。本節は、次のいずれも確定した事実としては述べない。

- MusicXML エンコーディングの再配布が許可されていること
- 世界向け GitHub 公開が法的に問題ないこと
- パブリックドメイン楽曲であれば MusicXML も当然公開可能であること
- music21 corpus のライセンスだけで現行テスト素材の再配布可否が確定すること

#### 秘密情報・認証情報（Confidential Data Policy）

| 禁止事項 | 対象 |
|---|---|
| ソースコードへの記載禁止 | API キー・トークン・秘密鍵・パスワード・個人情報 |
| Git 管理対象への記載禁止 | 同上（`.env`・設定ファイル・コメントを含む） |
| ログ・標準出力への出力禁止 | 同上（検査結果への混入を禁止） |

プロトタイプ検証段階では外部サービス連携を持たないため API キー等は不要である。

#### 外部 OMR サービスデータポリシー

score-reader 自体は外部ネットワーク通信を行わない。入力 MusicXML の生成過程で利用者が外部 OMR サービス（Newzik 等）を利用する場合、利用規約・著作権条件を事前確認し、出力 MusicXML を正解データとして扱わない。

### 5.5 Encryption, Masking, and Logging Policy（暗号化・マスキング・ログ取得方針）

| Type（種別） | Target（対象） | Policy / Method（方式・方針） |
|---|---|---|
| Encryption（暗号化） | 入力 MusicXML・出力データ | 本文書では対象外。理由: ローカル実行ツールであり、OS のファイルシステム保護に委ねる |
| Masking（マスキング） | 秘密情報 | ソースコード・出力・ログに秘密情報を含めないことで対応 |
| Logging（ログ取得） | 実行ログ・アクセスログ | プロトタイプ検証段階では対象外。標準出力への検査結果出力のみ。集中管理しない |

**データ保持方針**

| データ種別 | 保持方針 |
|---|---|
| 入力 MusicXML | 利用者のローカル環境で管理。score-reader はコピーを作成しない |
| 出力テキスト / JSON | 標準出力のみ。保存期間は利用者に委ねる |
| テスト素材 | 権利方針・現在の扱い、および未解決事項は §5.4 および TBD-005 を参照する |

### 5.6 Security Design Specifications（セキュリティ設計仕様）

セキュリティ要求レベルは `02_REQUIREMENTS_DEFINITION.md` §5.2 に記載する。

| Type（種別） | Design Specification（設計仕様） |
|---|---|
| Authentication（認証） | 対象外。理由: ローカル実行ツールであり、ユーザー認証機能を持たない |
| Authorization（認可） | 対象外。理由: ユーザー管理機能を持たない。OS のファイルシステム権限に委ねる |
| Access Control（権限管理） | score-reader プロセスは入力 MusicXML の読み取りのみ許可。書き込み・削除・派生ファイル生成は禁止 |
| Communication（通信） | score-reader 自体はネットワーク通信を行わない |
| Data Storage（データ保存） | ファイルを永続保存しない。入力は読み取り専用、出力は標準出力のみ |
| Data Disposal（データ廃棄） | score-reader が生成するデータはない（標準出力は OS が管理） |
| Personal Data Protection（個人情報保護） | 個人情報を収集・保存・送信しない |

#### セキュリティリスクの整理

| リスク | 対策方針 |
|---|---|
| 著作権保護楽譜のリポジトリ混入 | テスト素材の権利は §5.4 および TBD-005 を参照する |
| 外部 OMR サービスへの著作権楽譜送信 | 送信前に利用者が著作権状況・利用規約を確認 |
| API キー等の秘密情報混入 | プロトタイプ検証段階では外部 API 連携なし。将来検討事項として環境変数管理を検討（本書 TBD-001） |
| OMR 出力の誤信 | 出力に「確認対象データ」「完全無欠を保証しない」旨の注記を含める |

### 5.7 Comparison Data（比較データの設計）

採用済み要件は `02_REQUIREMENTS_DEFINITION.md` §5.8.1 を正本とする。以下は保持情報の設計方針であり、初回承認範囲の外部JSONフィールド・型は§5.9で具体化した。初回外の追跡・互換性判断はTBD-002に残す。既存の単一入力・標準出力の仕様を変更せず、比較用データは実行中のメモリで扱う案とする。

| 情報 | 保持方法の推奨案 | 不明・曖昧な場合 |
|---|---|---|
| 入力元 | 実行内で一意な入力識別子と安全な表示名。OMR 名・バージョン等は提供された場合だけ出典付きで保持 | OMR 名をファイル名から推定しない。入力識別子と OMR の種類を混同しない |
| パート | 入力内の出現順、元の識別子、名称を別に保持。入力間の対応は別の対応記録で管理 | 同名・重複識別子を同一パートと決めない |
| 譜表・声部 | 元の譜表番号・声部識別子と入力内の対象要素への参照を保持 | 欠落を自動的に「1」と補わず、適用可能な規則の有無と不明理由を記録。番号の一致だけで入力間対応を決めない |
| 小節 | 入力内の出現順と元の小節番号文字列を併記。番号重複・欠落・弱起を区別 | 番号だけを一意キーにしない。番号未記載でも入力内の出現順から追跡するが、原本の小節番号とは断定しない |
| 小節内位置 | 小節先頭からの四分音符単位の位置を分数で表し、元要素の順序・対象範囲も保持 | 位置を算出できない場合は不明理由と元要素参照を保持。装飾音や同時刻の複数音を時刻だけで一意化しない |
| 音楽情報と正規化 | 元の音高・音価・休符・和音構成、調号・臨時記号・移調情報、比較用値、適用規則と版を保持 | 解釈できない属性や未対応の記譜を欠損音・正常音へ置き換えない |
| 対応記録 | 入力ごとの局所位置、対応成立範囲、判断に用いた事実、対応状態と不能理由を保持 | 対応候補を確定対応と混同しない。共通位置を作れない場合も各入力の位置を残す |
| 個別警告と集約結果 | 個別警告の識別子・検査種別・理由・入力元・局所位置・観測値を保持し、集約結果から参照する | 複数理由を代表理由一つに置換しない。集約不能な警告も出力対象に残す |
| 原本確認情報 | 確認する事項、優先順位と理由、判定不能の理由を分けて保持 | 不明な順位を低優先として補わない |
| 原本 PDF の位置 | 提供・確認された位置情報とその出典のみ保持する案 | ページ・座標を取得できなければ「不明」。MusicXML の改ページや小節順から原本 PDF のページ位置を推測しない |

入力内の位置と入力間の共通位置は別物である。安定した入力元参照を保つため、読み込み時の元要素と比較用データの対応を残す案を推奨する。要素参照の形式やファイル識別の持続期間も TBD-002 の判断対象とする。対応成立条件・正規化方式そのものは `02_REQUIREMENTS_DEFINITION.md` TBD-005 / TBD-006 に集約し、本書では再決定しない。

出典を残すために入力全文・絶対パス・自由記述メタデータを無制限に出力することは提案しない。個人情報・秘密情報を除いた識別情報と必要な観測値を対象とし、安全な表示名の指定方法・出力項目の選別は TBD-002 と `04_UI_AND_FLOW_DESIGN.md` TBD-001 で整合させる。原本 PDF の自動解析・送信や保存機能は追加しない。

#### 5.7.1 Axis Results and Evidence（比較軸と根拠の保持案）

記音・実音・種類・開始位置・持続時間・和音構成について、観測値、入力内位置、対応先、比較状態、必要だった情報、不能理由を個別に保持する案とする。実音が記音と移調量に依存する場合、その依存を明記する。記音を解釈できない状態で同じ導出経路の実音だけを有効にしない。独立した出典のない実音値を作らない。

高リスク記譜の存在情報（タイあり、連符あり等）と、確認を求める根拠（未対応のため比較不能、接続不整合、入力間差分等）を別に保持する案とする。存在情報だけで高優先の警告を作らない。優先順位不明と位置不明も別に表す。集約は対応済みパート・譜表・声部・小節・開始位置・対象範囲の一致を条件とし、音符と小節全体を一つの対象に潰さない（`02_REQUIREMENTS_DEFINITION.md` TBD-005）。

内部のフィールド名・型・識別子の生成方法は Work が設計する。外部出力で情報を失わせる変更、実行間追跡の約束、互換性の変更だけを本書 TBD-002 と `04_UI_AND_FLOW_DESIGN.md` TBD-001 のユーザー判断対象とする。

### 5.8 Reusable Comparison Fixtures（共通テストデータの保存・版管理）

**採用済み**: 自作 MusicXML とケース ID、変更箇所・内容、期待結果をセットで Git 管理する。基準データは上書きせず、変更理由と版を記録する。既存公開素材の権利判断を流用せず、自作素材の由来を記録する。以下の配置で共通データを作成した。現行スイートは v003（変更理由・旧版はデータ側のCHANGELOGに記録）。

**承認済み配置**: 既存の `prototype/` と `docs/` を維持し、今後の正式実装向けに次を追加する。配置名や内部の記録形式を個別の承認事項にはしない。

```text
tests/fixtures/comparison/
  README.md                        # 自作方針、利用方法、由来・適用条件
  CHANGELOG.md                     # データ版・ケース版の変更理由
  suites/v001.json                 # ケースID・版・期待結果版・ファイルSHA-256の固定一覧
  bases/BASIC-4M/v001/base.musicxml # 上書きしない4小節の基準
  cases/SYN-001/v001/
    case.json                      # 入力参照、意図した変更、仕様案の承認状態
    variant.musicxml               # 変更版。不要なケースでは省略し基準を参照
    expected.json                  # 場所・軸・理由・優先順位・集約の期待結果
```

基準版、ケース版、期待結果版、スイート版（実行するケース集合の固定一覧）を区別する。期待結果には対応する設計版・節と承認状態を記録する。未承認の期待結果は提案であり、合格判定の正本にしない。SYN は人工ケースの識別子とし、実 OMR ケースは別の識別子・データ集合で管理する。

基準、変種、期待結果を修正するときは旧版を残して新しい版を追加し、理由・影響するケース・前版との関係を記録する。同じケース ID のまま内容を黙って置換しない。期待結果だけを変えた場合も新版とする。追加ケースは新しい ID とし、スイートの新しい版で採用する。ファイル内容の照合には SHA-256（内容を識別する値）を使う。

ケース記録には、基準と変種の相対パス・版、入力A/Bの役割、変更前後のパート/譜表/声部/小節番号と出現順/開始位置/元要素、変更前後の値、意図した差、期待する報告と出てはいけない報告を含める。欠落ケースは、消した側の元位置と残った側の位置を区別する。ケース記録や期待結果は検証側だけが参照し、製品の比較処理へ正解・対応付け情報として渡さない。

原本を転載しない自作素材を用いる。既存の `prototype/tests/` からコピー・加工して自作と呼ばない。データの利用条件・由来の記録は作成時に確認する。市販譜由来の中間ファイルはこの共通データに含めず、TBD-002 / TBD-005 の判断を後段の使用前に行う。製品の非永続化・非破壊制約と、開発用共通テストデータのGit保存は区別する。

### 5.9 Initial Report Schema（初回実装の外部データ）

初回レポートの `schema_version` は `1`、比較規則は `initial-2026-11-01-v1`。JSONはオブジェクト1個とする。パス・楽譜タイトル等の自由記述メタデータは出力しない。入力の指定順をA/Bとし、内容のSHA-256を付ける。読み取れない入力のSHA-256はnullとし、正常取得を装わない。

- `status`: complete / partial / unavailable。completeは初回の対象軸について処理した意味であり、原本に対する正確性ではない。
- `inputs`: A/Bと入力内容のSHA-256。`matches`: パートIDと両側の対応成立した小節出現順。イベント比較不能でも小節対応自体は記録する。
- `records`: ID、scope（part/range/measure/event）、両側のlocations、axes、全reasons、観測detail。reasonはcode/priority/detail/a/b/check_originalを持つ。
- `locations`: input、part、part_order、measure（1始まりの出現順）、measure_number（元文字列）、position（四分音符単位の分数文字列）、staff、voice、elements（小節内note要素の1始まり出現順）。不明はnull、対応のない側の要素は空配列。小節番号だけを識別子にしない。
- `axes`: kind/duration/written_pitchまたはcomposition/note_count/sounding_pitch/display。軸のstatusはequal/different/unavailable/not_applicable。a/bの観測値と不能理由を別に保持する。小節recordにはlength軸も持つ。
- `detail`: 入力ごとの元step/alter/octave/duration/type/dots、解釈時のdivisions/fifths、移調量、解釈値、不能理由、元要素参照、適用正規化。正規化前の値は比較用データと区別する。
- `reviews`: 同じscopeと両側位置が一致したrecordのみ集約し、record_ids、全reasons、representative_priority、has_unknown_priority、display_priorityを残す。PDFのページ位置は常にnull。
- `presence`: タイ・連符・装飾音・スラー等の存在と元要素。存在情報だけで警告を生成しない。`errors`: 入力読取失敗。`limitations`: 常時付ける検査限界。
- `summary`: review_locations、reasons、matched_measures、compared_events。matched_measuresは音符比較完了件数ではない。未対応や判定不能を合格件数に数えない。

製品は読み取りと標準出力のみで、入力やレポートを自動保存しない。保存は利用者の出力先指定（シェルのリダイレクト）または開発用検証ツールが担う。既存プロトタイプのJSON形式は変更せず、同形式との互換性を約束しない。外部利用者に影響する将来の形式変更はTBD-002/04 TBD-001で判断する。

## 7. Handoff to Detail Design（詳細設計への引き継ぎ）

1. **非破壊仕様の徹底**: 入力 MusicXML ファイルを変更・削除・複製しないこと（§5.3 参照）。
2. **秘密情報の混入防止**: API キー・トークンをソースコード・標準出力・ログに含めないこと（本書 TBD-001）。
3. **テスト素材の権利確認**: 権利方針・現在の扱い、および未解決事項は §5.4 および TBD-005 を参照する。技術的な由来は `05_ARCHITECTURE_DESIGN.md` TBD-005 を参照する。
4. **OMR 出力の誤信防止**: 検査結果に「確認対象データ」「完全無欠を保証しない」旨の注記を含めること（§5.6 参照）。
