## 1. Purpose（目的）

**初回実装の承認（2026-11-01、ユーザー）**: 2入力、02 §5.8.3〜5.8.5の初回判定表に基づく対応・部分比較、P1/P2/P3/U、個別根拠を保持した集約、共通テストデータ保存、および15ケースの期待報告を初回範囲として承認した。3入力以上・一般の多声部対応・実 OMR 効果検証は未承認/未実施のまま維持する。本書の初回範囲はこの承認で確定し、範囲外の提案・ASKMEへ拡張しない。


本文書は**プロトタイプ検証段階**における `verify_score.py`（単一 MusicXML 構造検査の検証実装）の利用手順・確認手順・人間レビュー方針、および将来の開発者・保守者への引き継ぎ事項を定義し、実装・運用・引き継ぎフェーズの基準とすることを目的とする。

引き継ぎ思想は、「機械にできること」「機械では確定できないこと」「人間が判断すべきこと」の境界判断を将来の開発者・保守者へ渡すことである。開発目的の分類は `01_REQUEST_DEFINITION.md` §1 を参照する。

開発段階の境界は `01_REQUEST_DEFINITION.md` §2 Development Stage Classification を参照する。現行プロトタイプは凍結中である。本実装確定スコープ（`02_REQUIREMENTS_DEFINITION.md` §5.8）への引き継ぎ事項は、本文書 §5.1 および Open Issues で管理する。比較機能の実装可否は確定済みである。本文書の対象読者は、設計者・実装者・利用者・将来の保守者・プロジェクトオーナーである。

## 4. Assumptions（前提条件）

本文書の内容が成立するために必要な前提は `01_REQUEST_DEFINITION.md` §4 を継承する。以下は運用・引き継ぎフェーズで追加する前提を示す。

**利用環境**

- macOS 上で動作する Python 3.x のローカル環境。特定の macOS バージョンは固定しない。Windows および Linux の動作保証・動作検証は対象外
- Git リポジトリをローカルにクローン済み

**Prototype の位置づけ**

- `verify_score.py` は技術検証用プロトタイプであり、正式完成版ではない
- 現行プロトタイプは凍結中である
- **`[WARN]` / `[ANOMALY]` が 0 件であっても、MusicXML の完全無欠を保証しない**
- 最終的な正確性の担保は原本 PDF との人間による目視照合で行う

**既知の限界（Known Limitations）**

| 限界 | 内容 |
|---|---|
| 音高正誤の自動判定不可 | MusicXML のみでは確定できない |
| 検査[3][4] | 検査[3][4]の第1パート制約および関連未決事項は `02_REQUIREMENTS_DEFINITION.md` を参照する |
| 和音・パート不一致の正解断定不可 | 原本 PDF 照合が必要 |
| タイ・スラー・連符・装飾音 | プロトタイプ検証段階の検査スコープ外 |
| `--json` 時のパース失敗 | 現行は JSON ではなくプレーンテキスト `[FATAL]` |

## 5. Definition Details（定義内容）

### 5.1 Handoff Items to Detail Design（詳細設計への引き継ぎ事項）

将来の開発者・保守者へ渡す引き継ぎ事項を示す。

| ID | Handoff Item（引き継ぎ事項） | Details / Background（詳細・背景） |
|---|---|---|
| HO-001 | 「推測しない・断定しない」原則 | 確定できない結果は `[WARN]`/`[INFO]` で列挙。黙殺・自動補完を行わない |
| HO-002 | 検査[3][4] | 検査[3][4]の第1パート制約および関連未決事項は `02_REQUIREMENTS_DEFINITION.md` を参照する |
| HO-003 | 非破壊仕様 | 入力 MusicXML の読み取りのみ。派生ファイル生成禁止 |
| HO-004 | 警告 0 件時の注記 | 「完全無欠を保証しない」注記を Output Formatter に組み込む |
| HO-005 | music21 バージョン固定 | `music21==10.3.0`。変更時は全検査再検証 |
| HO-006 | 著作権・秘密情報の非混入 | 著作権保護された譜面を公開リポジトリへ登録しない。テスト素材の権利は HO-008 を参照する |
| HO-007 | 本実装確定スコープ | 初回2入力範囲を実装（全体の確定機能は維持し、初回外は未実装）。機能の正本は `02_REQUIREMENTS_DEFINITION.md` §5.8。開発段階の境界は `01_REQUEST_DEFINITION.md` §2 Development Stage Classification を参照する。現行プロトタイプは単一 MusicXML 構造検査のまま凍結する |
| HO-008 | テスト素材の権利 | 権利方針・現在の扱い、および未解決事項は `03_DATA_AND_SECURITY_DESIGN.md` §5.4 および TBD-005 を参照する。技術的な由来は `05_ARCHITECTURE_DESIGN.md` TBD-005 を参照する |
| HO-009 | 性能の定量基準 | プロトタイプ検証段階では性能の定量的な合否基準を設けない。実行時間は必要に応じて測定対象にできる。本実装段階の性能基準は、必要時に別途定義する |

#### プロトタイプ検証項目（技術検証済み [1]〜[8]）

以下の検査項目 `[1]`〜`[8]` は、**正式仕様ではない**。現行 `prototype/src/verify_score.py` で確認済みの**プロトタイプ検証段階の技術検証項目**として記録する。機能要件の詳細は `02_REQUIREMENTS_DEFINITION.md` §5.1、実装上の参照範囲・制約は `05_ARCHITECTURE_DESIGN.md` §5.3 を参照する。

| ID | 検証項目 | 概要 |
|---|---|---|
| [1] | 移調楽器テーブル | 各パートの移調楽器情報（有無・半音差・方向）を報告する |
| [2] | 小節長の検算 | 各パートの各小節について、拍子記号に対する音価合計を検算する |
| [3] | 調号 | 調号を列挙する。制約は `02_REQUIREMENTS_DEFINITION.md` FR-004 |
| [4] | テンポ・拍子イベント | 拍子記号とテンポ変化を列挙する。制約は `02_REQUIREMENTS_DEFINITION.md` FR-005 |
| [5] | Unpitched（無音高）要素の報告 | スコア全体の `Unpitched`（無音高）要素の件数を報告する |
| [6] | リハーサルマークと小節番号の対応 | 全パートからリハーサルマークを収集し、小節番号との対応を出力する |
| [7] | 和音の音数チェック | 各パートの和音について構成音数を集計・報告する |
| [8] | パート間小節数整合チェック | 各パートの小節数を比較し、一致・不一致を報告する |

### 5.2 Implementation Constraints and Notes（実装時の注意点・制約）

| 制約 | 内容 |
|---|---|

### 5.3 Test Policy and Acceptance Criteria（テスト方針・受け入れ基準）

ビジネス観点での成功基準は `01_REQUEST_DEFINITION.md` §5.5 の SC-001〜SC-009 に記載する。

| Type（種別） | Policy / Criteria（方針・基準） |
|---|---|
| Unit Test（単体テスト） | プロトタイプ検証段階では正式な単体テストフレームワークを整備しない。現行テスト素材で手動確認する。権利の扱いは `03_DATA_AND_SECURITY_DESIGN.md` §5.4 を参照する |
| Integration Test（結合テスト） | `verify_score.py` を実際に実行し、検査 [1]〜[8] の出力・終了コードを目視確認 |
| System Test（システムテスト） | 正常系（警告あり・なし）と異常系（パース失敗）を手動確認 |
| Acceptance Test（受け入れテスト） | `01_REQUEST_DEFINITION.md` SC-001〜SC-009 を満たすこと。HC-001〜HC-005 の「判定しないこと」を出力で確認 |

#### 人間レビューチェックリスト（Human Review Checklist）

```
【実行前】
□ 著作権状況・外部 OMR 利用規約を確認した
□ 仮想環境を有効化した

【実行後】
□ [FATAL] / [ANOMALY] / [WARN] を確認した
□ 警告 0 件でも完全無欠を保証しないことを確認した

【原本 PDF 照合】
□ MuseScore 等で MusicXML を開き、原本 PDF と目視照合した
□ 音高・和音・タイ/スラー等は人間が判断した（score-reader は判定しない）
```

#### 人工的な誤りによる動作検証案

Work が自作の数小節と既知の変更箇所・変更内容を記録した検証用入力を用意する進め方は承認済みである。共通データとしての保存・再利用は §5.8 に従う。これはテスト入力の準備であり、製品に自動修正・派生 MusicXML 生成を追加するものではない。今回の作業では素材を生成・変更しない。

| 観点 | 検証ケース案 | 確認する結果 / 要件 |
|---|---|---|
| 拍数が正常な誤り | 音高だけの変更、音価を相殺する変更、音符と休符の置換、和音音数を保った構成音変更 | 拍数正常でも承認範囲の差分を報告する（CMP-001） |
| 音高解釈 | 調号変更、臨時記号の適用範囲、移調指定の相違・欠落、記音差と実音差 | 正解を断定せず、未解釈を一致にしない（CMP-001 / CMP-005） |
| 表現差だけの入力 | 承認済みの等価表現、単位の違い、和音要素の順序差。別途、タイ分割・異名同音・声部番号差等の境界例 | 正規化による不要な警告と差分の消失を双方確認。未承認の同一視は行わない |
| 位置の誤対応 | 小節欠落の疑い、番号重複、弱起、同名パート、複数譜表・声部、同時刻の複数音 | 対応不能を報告し、以降を機械的にずらして比較しない。別の音を同一位置とする誤対応を数える（CMP-002） |
| 警告の集約 | 同一音に複数理由、同じ小節の別声部・別位置、位置不明の複数警告 | 同一箇所だけを集約し、理由と出典が欠落しない（CMP-003） |
| 一致と検査限界 | 複数入力に同じ人工誤り、全入力で一致する未対応記譜、解析不能入力 | 共通誤りを検出できない限界を記録し、一致を安全宣言にしない。検査不能を正常にしない（CMP-005） |
| 表示と優先順位 | 低優先、順位不明、局所位置不明、原本 PDF ページ情報なし | 全確認対象を残し、不明表示・確認事項・個別根拠を保持。ページを捏造しない（CMP-002 / CMP-004） |
| 入出力の境界 | 一部入力の読み込み失敗、引数誤り、既存単一入力、テキスト / JSON | 承認された継続条件・終了コード・互換性を検証。入力が非破壊であることを確認 |

#### 実 OMR 出力による効果検証案

権利確認済みの原本と、利用が許可された実 OMR 出力を対象に、人間が原本と照合した記録を参照データとする。判定に迷う箇所は保留とし、原本に基づく誤り・正しい記譜・判断不能を分離する。対象サービスと素材条件は `01_REQUEST_DEFINITION.md` TBD-004、権利・保存場所は `03_DATA_AND_SECURITY_DESIGN.md` TBD-005 / TBD-002 で判断する。今回 OMR への送信や実測は行わない。

- **見逃し**: 人間が確認した誤りのうち、対象箇所が確認候補にならなかったもの。対応範囲内の見逃し、範囲外、判定不能を別に記録する。
- **不要な警告**: 原本上は正しく、確認作業に不要だった警告。正しい記譜に対する有用な注意喚起と区別し、不要と判断した理由を残す。
- **誤対応**: 異なる位置同士を対応させた件数・範囲。誤対応により生じた差分と、その後続区間への影響を記録する。
- **確認負荷**: 集約前の個別警告数、集約後の確認箇所数、失われた理由の有無、低優先・順位不明を含む確認時間を記録する。警告数減少だけで改善としない。
- **測定条件**: 素材の記譜特性、入力の出典と版、ツール・規則の版、承認された比較範囲、原本照合の判断根拠と保留理由を残す。原本・個人情報を公開記録へ無条件に転載しない。

測定単位（音符・箇所・警告）、分母、同一誤りの重複計数、保留の除外規則、受け入れ基準は本書 TBD-002 と `01_REQUEST_DEFINITION.md` TBD-003 で判断する。推奨は、見逃し・不要警告・誤対応を件数と内訳で先に示し、分母が確定してから率を併記する方法である。対象数ゼロ・未実測は成功率 100% としない。

人工誤りの動作検証が通っても、実 OMR での検出効果や時間削減を実証したとは扱わない。効果を比較する場合は同等の素材・確認条件で既存の確認手順との差を記録する。判定不能な素材を除外して結果を良く見せない。

### 5.8 Reusable Synthetic Cases（共通の自作ケースと承認済み期待結果）

**採用済みの進め方**: Work が数小節の自作 MusicXML を用意し、既知の差の動作確認を先行する。データは一時ファイルにせず、`03_DATA_AND_SECURITY_DESIGN.md` §5.8 の配置案で Git 管理する。実 OMR の精度・時間削減は後段で検証する。以下の入力差・期待結果は2026-11-01に承認された初回受け入れ条件である。実行結果は保存した検証記録に示す。

#### 5.8.1 Input and Expected Reports（入力差と期待報告の対）

基準 BASIC-4M: P1、譜表1、声部1、小節番号1〜4、4/4、調号変化なし、明示的な移調量0。各小節を `C4(1), D4(1), 休符(1), [C4,E4,G4](1)` とする。括弧は四分音符単位の長さ、開始位置は順に0,1,2,3。Aは基準、Bはケースごとの変種。全ケースは独立に基準から用意し、前のケースの変更を引き継がない。

| ケース ID | 意図的な入力差 | 期待する報告 / 出してはいけない報告 |
|---|---|---|
| SYN-001 一致 | A/Bとも基準 | 対応範囲・比較軸内で差分0、比較不能0、確認候補0。完全無欠とは表示しない |
| SYN-002 音高差 | Bの小節2、位置1のD4をE4へ変更、長さ1は保持 | 同位置に記音差・実音差、音価一致。P2の確認箇所1、理由は2軸とも保持。拍数正常で差を抑制しない |
| SYN-003 休符差 | Bの小節2、位置2の休符(1)をF4(1)へ変更 | 種類差、音価一致、休符側の音高は対象外。P2の確認箇所1。休符の音高を推測しない |
| SYN-004 和音差 | Bの小節2、位置3の[C4,E4,G4]を[C4,F4,G4]へ変更 | 和音構成差（E4/F4）、音数3・音価1は一致。P2の確認箇所1。音数一致だけで一致にしない |
| SYN-005 音価差 | Bの小節2をC4(3/2),D4(1/2),休符(1),和音(1)へ変更 | 位置0で音価差。Aの位置1とBの位置3/2はそれぞれ片側のみのイベント（P2）。位置2,3は比較継続。拍数合計4のままで差を報告し、D4同士を強制対応させない |
| SYN-006 小節欠落 | Bから小節2を除き、残る番号は1,3,4 | 小節1は比較可能。Aの2〜4/Bの3〜4は対応不能、P1。どちらが原本の何小節を欠落したか断定しない。後続音を大量の音高差に変換しない |
| SYN-007 番号重複 | Bの小節3の番号だけを2へ変更し1,2,2,4にする | 小節1のみ比較可能。番号2の2位置を示し、それ以降は対応不能、P1。最初の番号2を勝手に正しい方と選ばない |
| SYN-008 同名パート | 自作の2パート基準版を別途用意。A=P1/P2、B=X1/X2で全て同名 | パート対応不能、P1。順番や音の類似度で対応を補わない。補助ケースとして両側P1/P2が一意で構成も一致する場合は対応可能を確認する |
| SYN-009 声部番号差 | Bの唯一の声部番号を全小節1→7へ変更 | 単一声部同士として対応、元番号を保持、音楽内容の差分0。多声部化した場合はこの規則を適用しない |
| SYN-010 正規化 | Bのdivisionsと全durationを同率で2倍にし、和音内の構成音順を変更 | 比較用位置・音価・和音は一致。不要な差分警告0。元値と規則は保持 |
| SYN-011 部分比較 | Bの明示的な移調要素だけを除く。記音・位置・音価は基準と同じ | 記音・種類・音価一致を保持。実音は比較不能、P2。各小節の同じ原因を示し、通常の一致を実音一致へ転用しない |
| SYN-012 記音差・実音一致 | Aの移調量を-2にした自作基準版と、記音を全て2半音下げ移調0としたBを用意 | 記音差と実音一致を併記。音価・種類一致を保持。実音一致を理由に記音差を消さない |
| SYN-013 警告集約 | Bの小節2、位置1をD4(1)→E4(3/2)へ変更。以後の位置も変化する | 位置1の記音差・実音差・音価差を1確認箇所へ集約し全理由を保持、代表P2。小節長不一致は小節単位の別確認対象。後続位置差も別対象であり、全警告を1件に潰さない |
| SYN-014 高リスク記譜 | 自作の補助版で両入力に同じタイまたは連符を設ける | 存在情報を記録。初回未対応の軸は理由付きP2。時間軸が解釈不能なら依存範囲をP1。存在だけで全件P1にしない。独立した通常小節は比較を継続 |
| SYN-015 表示差 | 解釈音高を同じに保ち、Bの一つの臨時記号表示だけを変更 | 音高一致と表示差を区別しP3。音高誤りとは報告しない |

SYN-008/012/014の補助基準も独立した基準ID・版として保存し、BASIC-4Mを変更しない。SYN-011は `02_REQUIREMENTS_DEFINITION.md` §5.8.5 の保守的な移調条件案を検証する。ライブラリが既定値0を返しても元入力に明示があるかを区別する。XMLを不正と報告するケースではない。

順位集約の境界は追加の検証入力として、同一箇所のP1+P2は代表P1、P2+UはU枠かつ既知代表P2、別位置の同じ理由は別箇所、存在情報だけは警告へ昇格しないことを確認する。Uは未分類結果を扱う出力・集約の検証データで確認し、無理にMusicXMLから発生させない。この補助データもケースと同じ版管理対象とする。今回承認に基づき、期待する個別理由・場所・集約数と禁止する報告を固定し、実装結果から期待結果を逆算しない。

#### 5.8.2 Reproducible Runs（実行状態の記録）

検証結果にはスイート版、全ケースID/ケース版/期待結果版、入力と期待結果のSHA-256、使用実装のcommit、作業ツリーが未commitか、実行条件・依存版・規則版、実出力と期待結果との照合結果を記録する。記録は開発用であり、製品にログ保存機能を追加するものではない。

未commitの実装はcommit番号だけで識別しない。HEADを基準とする追跡対象の差分（ステージ済み・未ステージを含む最終状態）を保存し、そのSHA-256を記録する。実行に使った未追跡ファイルも相対パス・内容・SHA-256を保存する。削除・バイナリ変更を含め復元できる形式とし、実行に関係するGit管理外設定も秘密情報を除いて識別する。取得できなければ再現可能と表示しない。実行前後の内容識別値が変わった実行は比較対象から外し、再実行する。

結果の配置は開発用の `tests/results/comparison/<run-id>/` を提案する。結果・差分は保持し、公開Gitへの登録は秘密情報・権利を確認したものに限る。共通の自作データをGit管理する方針と、実行結果を全て無条件に公開することを混同しない。初回基準実行と再実行を別のrun-idで保存する。

#### 5.8.3 Before and After Comparison（同じ期待結果での変更前後比較）

1. 変更前後で同じスイート版・入力内容・期待結果版を実行する。未commit実装なら上記差分も固定する。
2. 見逃しは期待する確認対象・理由が出ないもの、不要警告は期待外の確認対象・理由、誤対応は期待する対応範囲以外を一致箇所として扱ったものとして記録する。重複理由、誤集約、順位誤り、未処理も別に記録する。期待上の比較不能を正しく報告したものを見逃しにしない。
3. 共通ケースはケースID・データ版・期待結果版・内容識別値が一致する集合とする。新ケースを加えた場合、共通ケースの前後比較と、新規ケースだけの結果を分ける。変更・廃止ケースも別枠とし、同じIDで期待結果を変えたケースを共通扱いしない。
4. 期待結果の訂正が必要なら理由を記録して新版を作り、変更前後の両実装を同じ新版で再実行する。旧結果も保持する。片側だけ新期待結果を使った率を比較しない。
5. 個別理由と集約後の箇所の双方を照合し、警告件数の減少だけで精度向上としない。実行不能・未実施を0件成功にしない。人工ケースの結果を実 OMR の精度・時間削減と合算しない。

最初の動作検証の受け入れ条件は、承認されたケースの期待報告を全て満たし、禁止した報告・誤対応・根拠の消失がないこととする（本書 TBD-002）。これは人工ケース内の動作条件であり、実 OMR の数値目標は `01_REQUEST_DEFINITION.md` TBD-003 / TBD-004 に残す。

### 5.9 Initial Acceptance Execution（初回動作検証の実行・再現）

リポジトリルートで次を実行する。検証先は未作成のディレクトリ名を指定し、過去の結果は上書きしない。現行の15ケース集合はv003。基準はv001、SYN-012はメタデータv003/入力v002/期待結果v001、他14ケースは全てv001。修正理由は共通データのCHANGELOG.mdを参照する。入力・期待結果は実装から生成しない。

```bash
python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 tools/verify_comparison.py --suite v003 --output tests/results/comparison/initial-20261101
python3 tools/verify_comparison.py --suite v003 --output tests/results/comparison/repeat-20261101 --compare-run tests/results/comparison/initial-20261101/result.json
```

15ケースごとに理由code・順位・位置・scopeの完全一致、対応小節一覧、集約箇所数、指定した軸の値/状態、存在情報、入力不変、個別理由の保存、PDF位置未補完を検証する。不要な理由も失敗とする。補助境界ケースは `tests/fixtures/comparison/support/v001/` に保存し、15ケースとは分ける。全15ケースと入力失敗について、CLIのテキスト/JSONが同じ全情報を持つことを別途検証する。

各runにresult.json、ケース別JSON/テキスト、boundary-tests.txt、source-state.json、tracked.patch、untracked.tar.gz、RESTORE.mdを保存する。source-stateにはHEAD、対象ソースのSHA-256、未追跡一覧、差分識別値を残す。HEADに対するバイナリ対応差分と未追跡ファイル実体から、別チェックアウトで当該実装を復元できる。復元後は全ファイルのSHA-256を照合する。実行前後のソース一致も検証する。結果フォルダは再帰的な自己収集を避け、実装スナップショットから除外する。

result.jsonはデータ集合版と識別値、ケース/期待結果/入力の識別値、実装commit、未commit状態、実装スナップショットの識別値、OS/Python、実行成否を保持する。先行実装が存在しない初回の結果を基準として保存する。再実行との比較は再現性確認であり、精度改善の主張にはしない。

`--compare-run`はケースIDとケース定義・入力・期待結果の識別値が一致するもののみcommon_casesへ置き、見逃し・不要理由・誤対応・箇所数・理由数を前後併記する。added_cases/changed_cases/removed_casesは別枠。集約・比較軸・入力保全等の失敗もerrorsとpassedへ残し、警告数だけで判定しない。実 OMR の精度・確認時間の効果検証は未実施である。
