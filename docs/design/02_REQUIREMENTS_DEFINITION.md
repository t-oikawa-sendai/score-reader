## 1. Purpose（目的）

本文書は**現行プロトタイプ**における `verify_score.py`（単一 MusicXML 構造検査の検証実装）が満たすべき機能要件・非機能要件を定義し、実装・検証フェーズの基準とすることを目的とする。

開発段階の分類は `README.md` §1 Development Stage Classification を参照する。機械と人間の役割境界は `README.md` および `01_REQUEST_DEFINITION.md` §1 を参照する。本実装確定スコープは §5.8 に分離する。詳細仕様は本実装時に定義する。現行プロトタイプの FR-001〜FR-012 と混在させない。自動修正、自動統合、Web UI は将来検討事項のままとする。原本 PDF 横並び表示は本リポジトリの対象外であり、本リポジトリでは設計・実装方針を定義しない。人間が MuseScore 等を使用して原本 PDF と目視照合する既存運用は維持する。本文書の前提となる背景・課題・要求は `01_REQUEST_DEFINITION.md` に記載する。本文書の対象読者は、設計者・実装者・プロジェクトオーナーである。

## 2. Scope（対象範囲）

| 対象 | 内容 |
|---|---|
| 開発段階 | **現行プロトタイプ**（`README.md` §1 Development Stage Classification 参照）。本実装確定スコープは §5.8 |

| 対象ファイル（プロトタイプ） | 単一 MusicXML ファイルの内部整合性検査 |
| 本実装確定スコープ | 複数 MusicXML 入力、正規化、比較可能性判定、差分比較、差分可視化、比較レポート生成。未実装。詳細は本実装時に定義する |
| インターフェース | CLI（コマンドライン引数による入力ファイル指定・出力形式選択） |
| 出力先 | 標準出力のみ（テキスト形式 / JSON 形式） |

## 3. Out of Scope（対象外範囲）

以下は本文書の要件定義対象外とする。

| 対象外項目 | 理由 |
|---|---|
| 音高・音価の正誤自動判定 | 現技術では確定できない。人間による原本 PDF 照合が必要 |
| 原本 PDF との内容一致確認 | MusicXML のみでは原本内容を復元・比較できない |
| 楽譜編集・修正・再出力機能 | score-reader は検査結果の出力に専念する非破壊ツールである |
| 複数 MusicXML の自動マージ・統合 | 自動修正、自動統合は将来検討事項。複数 MusicXML 比較自体は本実装確定スコープ（§5.8）であり、現行プロトタイプの FR には含めない |
| Web UI・GUI | 将来検討事項。プロトタイプは CLI ツールとして実装する |
| 外部 API の公開・提供 | プロトタイプ検証段階では外部 API を持たない（`05_ARCHITECTURE_DESIGN.md` TBD-003） |
| 音声再生・楽譜表示 | 検査結果の出力以外の UI 機能は対象外 |
| 完成版アプリケーションの本フェーズでの実装 | 本文書の FR-001〜FR-012 は現行プロトタイプに限定する。本実装確定スコープは §5.8 |

## 4. Assumptions（前提条件）

本文書の内容が成立するために必要な前提は `01_REQUEST_DEFINITION.md` §4 を継承する。以下は要件定義フェーズで追加する前提を示す。

- 入力 MusicXML は `music21.converter.parse` が読み込める形式であること
- 依存ライブラリは `music21 10.3.0` のみとする（`prototype/requirements.txt` 参照）
- 機能要件 FR-001〜FR-012 はプロトタイプ（`verify_score.py`）の**現仕様**に基づく
- 本実装確定スコープは FR-001〜FR-012 に混在させず、§5.8 に分離する
- 現行プロトタイプの将来実装要求（JSON 情報量等）は §5.7 に分離する
- `[WARN]` / `[ANOMALY]` が 0 件であっても、MusicXML の完全無欠を保証しないことを要件として扱う
- 現行プロトタイプは凍結中である

## 5. Definition Details（定義内容）

### 5.1 Functional Requirements（機能要件一覧）

本節の FR-001〜FR-012 は、現行プロトタイプの実際の動作を記載する。

#### 基本機能

| ID | Feature Name（機能名） | Priority（優先度） | Details（詳細） |
|---|---|---|---|
| FR-001 | MusicXML パース | High | コマンドライン第 1 引数で指定されたファイルを `music21.converter.parse` で読み込む。パース失敗時はプレーンテキストの `[FATAL]` を標準出力へ出力し、終了コード 1 で終了する。`--json` 指定時でも、パース失敗時の現行出力は JSON ではない |
| FR-010 | 人間可読テキスト出力 | High | デフォルト動作として、検査 [1]〜[8] の結果を人間可読テキスト形式で標準出力に出力する。出力順序: [1]→[2]→[3]→[4]→[6]→[7]→[8]→[5] |
| FR-011 | JSON 出力 | High | `--json` フラグ指定時、パース成功後に検査 [1]〜[8] の結果を構造化 JSON 形式で標準出力に出力する。パース失敗時は FR-001 のとおり JSON を出さない。テキスト出力にある一部の注記は JSON に存在しない（§9 Appendix / Known Limitations 参照） |
| FR-012 | 終了コード管理 | High | パース成功時: 終了コード 0。パース失敗時: 終了コード 1 |

#### 検査機能（[1]〜[8]）

| ID | Feature Name（機能名） | Priority（優先度） | Details（詳細） |
|---|---|---|---|
| FR-002 | [1] 移調楽器チェック | High | 各パートの移調楽器情報（有無・半音差・方向）を報告する。移調楽器が 1 件も検出されない場合、テキスト出力は OMR が移調情報を欠落させている可能性を注記する。この注記は現行 JSON には存在しない |
| FR-003 | [2] 小節長の検算 | High | 各パートの各小節について、拍子記号に対する音価合計（四分音符単位）を検算する。拍子未確定: `[WARN]`、期待と不一致: `[ANOMALY]`、アウフタクト許容条件（小節番号が 0 または 1、かつ実測音価が期待音価未満）: 許容し異常としない。ただしこれは簡易判定であり、すべての弱起を正しく判定する保証ではない |
| FR-004 | [3] 調号の列挙 | Medium | 第 1 パート（`score.parts[0]`）から調号を列挙し、出現小節番号・シャープ/フラット数を出力する。現行 CLI はこの第 1 パート限定の注記を出力しない。コード凍結中に受容している既知の制約である |
| FR-005 | [4] テンポ/拍子変化イベントの列挙 | Medium | 第 1 パートから拍子記号とテンポ（メトロノームマーク）の変化を小節番号順に列挙する。現行 CLI はこの第 1 パート限定の注記を出力しない。コード凍結中に受容している既知の制約である |
| FR-006 | [5] Unpitched（無音高）要素の報告 | Medium | スコア全体の `Unpitched`（無音高）要素の件数を報告する。JSON は 0 件を含む件数（`unpitched_count`）を出す。テキスト出力は 1 件以上のとき `[INFO]` 付きで件数を出し、0 件のときは件数行を出さない。件数が 0 でも完全無欠を保証しない旨の注記はテキストに出す |
| FR-007 | [6] リハーサルマーク対応表 | Medium | 全パートからリハーサルマークを収集し、小節番号との対応を出力する。重複排除は「小節番号 + マーク内容」の組で正規化する（同一内容でも小節番号が異なる場合は別マークとして扱う）。検出ゼロは異常でも `[WARN]` でもなく、レベルタグを付けない確認用注記とする。小節番号未確定、内容空、同一小節の複数マークは `[WARN]` のままとする |
| FR-008 | [7] 和音音数チェック | Medium | 各パートの和音（`chord.Chord`）について構成音数を集計・報告する。主流音数は「パート内の和音構成音数の最頻値」と定義する。単音が和音として記譜: `[INFO]`、構成音数が主流音数と異なる和音: `[WARN]`、和音 0 件: テキスト出力は取りこぼし可能性を注記する（この注記は現行 JSON には存在しない）。最頻値が同率の場合、現行実装は最初に出現した候補に依存する。正誤判定ではなく確認対象の抽出であり、音数の正誤は断定しない |
| FR-009 | [8] パート間小節数整合チェック | High | 各パートの小節数を比較する。パートが 1 つのみ: `[INFO]`、全パート一致: 一致結果を出力、不一致: `[WARN]`。どのパートが正しいか・どの小節が欠落したかは断定しない |

#### 出力レベル定義

| 出力レベル | 意味 |
|---|---|
| `[FATAL]` | パース失敗。処理を中断し終了コード 1 で終了 |
| `[ANOMALY]` | 小節長と拍子の不一致など、構造上の異常 |
| `[WARN]` | 要確認の疑い（拍子未確定・リハーサルマークの小節番号未確定/内容空/同一小節複数・和音音数の相違・パート間小節数不一致 など） |
| `[INFO]` | 参考情報（単音が和音として記譜・無音高要素が 1 件以上ある場合の件数 など） |

リハーサルマーク 0 件の確認用注記、および検査 [1][7] のテキスト専用注記は、上記レベルタグを付けない。

テキスト出力と JSON 出力の情報差は機能要件そのものではない。現行実装事実は §9 Appendix / Known Limitations に記載する。

#### JSON 出力フィールド定義（FR-011 補足）

以下はパース成功時の現行 JSON フィールドである。将来のフィールド名変更・エラー構造は未確定であり、§5.7 に分離する。

| フィールド | 内容 |
|---|---|
| `parts` | パート数 |
| `transposing_instruments` | [1] 移調楽器情報 |
| `measure_anomalies` | [2] 小節長異常（WARN / ANOMALY のみ） |
| `key_signatures` | [3] 調号 |
| `tempo_meter_events` | [4] 拍子・テンポ変化イベント |
| `rehearsal_marks` | [6] リハーサルマーク |
| `chord_voicing` | [7] 和音音数 |
| `unreadable` | [5] Unpitched（無音高）要素 |
| `part_measure_counts` | [8] パート間小節数整合 |
| `warnings` | 全セクションの WARN / ANOMALY を集約した配列 |
| `note` | 検査の限界に関する注記 |

### 5.2 Non-Functional Requirements（非機能要件）

セキュリティの設計仕様（著作権保護・情報管理の実装方針）は `03_DATA_AND_SECURITY_DESIGN.md` に記載する。

#### 基本非機能要件

| Type（種別） | Requirement（要件内容） |
|---|---|
| Performance（性能） | プロトタイプ検証段階では性能の定量的な合否基準を設けない。実行時間は必要に応じて測定対象にできる。本実装段階の性能基準は、必要時に別途定義する |
| Availability（可用性） | プロトタイプ・ローカル実行ツールのため、可用性の定量基準は規定しない |
| Security Requirement Level（セキュリティ要求レベル） | 低〜中。テスト素材の権利は楽曲・エンコーディング・再配布条件を分けて確認する。著作権保護楽譜・API キー・個人情報をリポジトリに含めない |
| Maintainability（保守性） | 検査項目の追加・変更が容易な構造を維持すること。依存ライブラリは `music21 10.3.0` のみとし、外部依存を最小化すること |

#### 非破壊要件

| 要件 | 内容 |
|---|---|
| 入力ファイル保護 | 入力 MusicXML ファイルを読み取るのみで、上書き・更新・削除を行わない |
| 派生ファイル出力禁止 | 修正済み MusicXML・派生 MusicXML を出力しない |
| 出力先制限 | 検査結果は標準出力（テキストまたは JSON）への出力に限る |

#### 設計原則要件（推測禁止・断定禁止）

| 要件 | 内容 |
|---|---|
| 推測禁止 | 読めない・断定できない箇所は黙殺せず `[WARN]` 等として列挙する |
| 断定禁止 | 「何音であるべきか」「どのパートが正しいか」等は推測・断定しない |
| 完全無欠の保証禁止 | `[WARN]` / `[ANOMALY]` が 0 件であっても、MusicXML の正確性・完全無欠を保証する表現・動作を禁止する |
| 完全自動化の約束禁止 | 出力結果が音高・原本一致の正確性を保証するような表現・動作を禁止する |

#### 人間確認要件

| 要件 | 内容 |
|---|---|
| 原本照合の必要性の明示 | 検査結果に「最終的な正確性は原本 PDF との目視照合で担保する必要がある」旨を含める |
| 検査限界の明示 | 音高の正誤・和音の正確性・パート間不一致の正解・タイ/スラー/連符等は判定しない旨を出力する |
| 複数 OMR 一致の誤解防止 | 本ツール単体では複数 OMR 間の一致を正解の根拠として扱わない |

#### 検査できないことの要件定義（Out of Scope 要件）

以下は score-reader が判定・保証しないことを要件として明示する。

| 判定しないこと | 理由 |
|---|---|
| 音高の正誤（符頭位置・加線・臨時記号・オクターブ違い） | MusicXML の構造検査では確定できない |
| 和音構成音数が原本譜と一致するかの断定 | 正解の定義が原本 PDF に依存する |
| パート間小節数不一致時にどのパートが正しいか | 原本 PDF を見ないと確定できない |
| どの小節が欠落・過剰認識されたかの特定 | MusicXML だけでは復元不能 |
| タイ・スラー・連符・装飾音の正誤 | 構造解釈に音楽的判断が必要 |
| 強弱記号・テキスト指示・アクセント等の欠落 | 検査対象外（プロトタイプ検証段階） |
| 複数 OMR 一致時の正しさの保証 | 同じ誤認識が起きる可能性がある |
| `[WARN]` / `[ANOMALY]` が 0 件の場合の完全無欠の保証 | 本ツールの検査限界によるもの |

## 7. Handoff to Detail Design（詳細設計への引き継ぎ）

アーキテクチャ設計（`05_ARCHITECTURE_DESIGN.md`）・実装フェーズへ引き継ぐ主要事項を示す。

1. **「推測しない」設計原則を実装に徹底すること**: 断定できない結果は `[WARN]` / `[INFO]` として列挙する。黙殺・自動補完・推測による埋め合わせを行わないこと（NFR §5.2 設計原則要件 参照）。

2. **FR-004・FR-005 の参照対象の制約を引き継ぐこと**: 調号・テンポ/拍子の列挙は「第 1 パート（`score.parts[0]`）のみ」である。現行 CLI は制約注記を出力しない。凍結中はこの欠落を受容する。出力注記の追加は §5.7 FUT-004。全パート対応の採用判断は本文書 TBD-002（親）、実装方針は `05_ARCHITECTURE_DESIGN.md` TBD-002、運用手順は `06_OPERATION_AND_HANDOFF.md` TBD-001。

3. **非破壊仕様を実装レベルで保持すること**: 入力ファイルの読み取り専用・派生ファイル出力禁止・標準出力限定は実装レベルで変更しないこと（NFR §5.2 非破壊要件 参照）。

4. **`[WARN]` / `[ANOMALY]` 0 件時の注記を出力に組み込むこと**: 警告 0 件であっても「完全無欠を保証しない」旨の注記を出力に含めること（FR-006、NFR §5.2 人間確認要件 参照）。

5. **現仕様と将来実装要求を混在させないこと**: FR-001〜FR-012 は現行動作に限定する。JSON 情報量統一・JSON エラー形式は §5.7 に残す。本実装確定スコープは §5.8 に残し、FR に混在させない。
